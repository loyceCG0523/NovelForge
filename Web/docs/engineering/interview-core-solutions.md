# NovelForge 核心难点与解决方案（面试准备）

## 1. 项目一句话介绍

NovelForge 是一个面向长篇网络小说的低干预自动创作系统。用户填写起始需求文档后，系统会自动生成作品圣经，以 6-12 章的闭环剧情事件为单位推进章节生成，并自动维护结构化记忆、执行连续性审校、事件级质量审校、自动修订和样本风格分析。

面试中可以这样说：

> 这个项目不是简单调用大模型写一章小说，而是把长篇小说生成拆成“规划、上下文构建、章节生成、记忆同步、质量审校、自动修订”的异步 Agent 工作流，解决长篇上下文、一致性、剧情闭环和 AI 味问题。

## 2. 难点一：长篇小说超出模型上下文

### 问题

网络小说通常几十万到上百万字，无法把全书正文一次性放进模型上下文。直接使用上一章摘要，会丢失对白节奏、人物状态、伏笔细节和场景氛围。

### 解决方案

实现 `ChapterContextBuilder`，为每章动态构建上下文包：

- 最近 3 章全文和摘要，保证近场文风和情绪连续。
- 作品圣经，保存全局设定。
- 合并后的结构化记忆，保存长期事实。
- 未完成伏笔和开放风险，约束后续生成。
- 样本分析风格向量，约束文风和节奏。
- 单章字数范围、风格参考、禁忌内容和自动化策略。

上下文快照写入 `chapters.context_snapshot`，方便回放和排查。

### 面试表达

> 我没有把上下文问题简单交给向量库，而是采用“近场全文 + 远场结构化记忆 + 全局作品圣经”的混合上下文策略。近场全文负责语言连续性，结构化记忆负责事实连续性，作品圣经负责全局约束。

### 可追问点

- 为什么不是只用 RAG？
- 为什么最近 3 章要用全文？
- 结构化记忆和章节摘要的区别是什么？

建议回答：

> RAG 适合召回片段，但长篇小说中人物状态、道具归属、伏笔状态是唯一事实，不能只靠语义相似召回。结构化记忆保存的是当前状态，章节摘要只是辅助。

## 3. 难点二：人物、伏笔和道具容易重复或冲突

### 问题

大模型生成多章后，经常出现同一人物多份设定、关系状态重复、伏笔忘记兑现、道具位置冲突等问题。

### 解决方案

实现结构化记忆体系：

- `MemoryAgent` 在章节生成后自动抽取人物、关系、地点、道具、事件、时间线和世界规则。
- `memory_extractor` 对实体名做规范化，例如去掉“女主”“男主”等前缀。
- 进入 Prompt 前不直接塞入所有历史记忆，而是按实体合并成实体级状态摘要。
- 章节删除时同步清理对应自动记忆。
- 前端支持手动删除记忆组和一键清空当前作品记忆。

### 面试表达

> 我把“记忆”从自然语言摘要改成数据库里的结构化事实，并且在进入模型输入前做实体合并，避免 Prompt 里出现大量重复事实。这样既节省上下文，又减少模型被冲突信息误导。

### 可追问点

- 人物记忆应该存什么？
- 怎么避免“许清禾”被抽取成多条重复人物？
- 删除章节后为什么要同步删除记忆？

建议回答：

> 人物记忆重点是稳定画像和当前状态，例如身份、性格、目标、家庭、关系、能力和当前位置，而不是把事件复述成人物信息。删除章节后，如果不清理该章自动抽取的记忆，就会出现数据库事实和正文不一致。

## 4. 难点三：一章一章生成导致剧情散

### 问题

如果只提供“启动章节 Agent”，模型容易每章解决小问题，但整段剧情没有完整起承转合，读起来像流水账。

### 解决方案

将自动生产单位从单章升级为“剧情事件”：

- 一个 `StoryEvent` 覆盖 6-12 章。
- `EventGenerationGraph` 先规划事件目标、核心冲突、章节计划。
- 再逐章生成正文。
- 每章生成后同步记忆和审校。
- 事件完成后执行事件级质量检查。

### 面试表达

> 我把“章节生成”提升到“剧情事件生成”。因为网文读者通常感知的是一个事件周期，而不是单章孤立质量。一个大事件内部有铺垫、冲突、升级、兑现和钩子，这样自动生成更接近真实连载节奏。

### 可追问点

- 为什么是 6-12 章？
- 事件级质量怎么评估？

建议回答：

> 6-12 章比较接近网文一个小副本或阶段冲突的节奏。事件级审校关注闭环程度、人物推进、节奏、伏笔推进和残留风险，不只看单章文字质量。

## 5. 难点四：用户不想处理生成过程

### 问题

小说创作系统如果频繁要求用户确认人物动机、伏笔、风险处理，会违背低干预目标。

### 解决方案

将风险处理从“用户待办”改为“系统自动处理记录”：

- `ContinuityChecker` 发现章节级风险。
- `EventQualityChecker` 发现事件级风险。
- `QualityAgent` 判断是否可自动修复。
- `RevisionAgent` 自动修订章节。
- 修订后重新审校。
- 前端只展示问题和修复历史。

### 面试表达

> 我的产品目标是用户填写起始需求后系统自动生产，因此风险不应该变成用户的待办列表。系统会自动修复可处理风险，前端只做透明展示，让用户知道系统发现了什么、修了几次、还有什么残留问题。

### 可追问点

- 自动修订会不会越修越坏？
- 如何防止无限循环？

建议回答：

> 当前单章默认限制自动修订次数，例如最多 2 次。每次修订都写入 repair_history，并重新跑审校。如果仍有风险，就记录为残留风险，而不是无限循环。

## 6. 难点五：AI 味和真人风格差异

### 问题

大模型常见问题包括解释性对白、抽象情绪、模板句式、节奏平均、缺少潜台词。

### 解决方案

实现 `SampleAnalysisAgent`：

- 用户上传优秀小说 TXT/MD 样本。
- API 保存文件到 MinIO，不把原文写入数据库。
- Worker 从对象存储流式读取。
- 按约 8000 字切片。
- 分片抽取文风、情绪、伏笔、对白、节奏指标。
- 聚合为 `sample_analysis.v2` 报告。
- 后续章节生成读取已完成样本的风格向量。

### 面试表达

> 我没有让模型直接模仿样本内容，而是把样本转成可迁移的工程特征，比如句长分布、对白占比、潜台词比例、章尾钩子类型、伏笔密度。这样既避免复制原文，也能把风格约束用于后续生成。

### 可追问点

- 百万字样本怎么处理？
- 为什么不用一次性放进 LLM？
- 样本原文如何保护？

建议回答：

> 百万字样本不能同步分析，也不适合进数据库。我使用“上传文件 + MinIO + Worker 异步切片 + Map-Reduce 聚合”的架构。数据库只保存 object key、状态、分片进度和最终结构化报告。

## 7. 难点六：长任务不能阻塞 API

### 问题

章节生成、事件生成、样本分析和自动修订都可能耗时很长。如果在 HTTP 请求中同步执行，会导致超时、页面卡死，也难以追踪失败。

### 解决方案

设计统一异步任务协议：

```text
API 创建 generation_tasks
  -> Redis RPUSH
  -> Worker BLPOP
  -> 执行任务
  -> 更新 status/progress/result_payload/error_message
  -> 前端轮询业务接口或任务接口
```

当前任务类型包括：

- `produce_novel`
- `build_story_bible`
- `generate_story_event`
- `continue_story_event`
- `generate_chapter`
- `check_story_event_quality`
- `analyze_sample`

### 面试表达

> 我把 API 和耗时 Agent 任务完全解耦。API 只负责鉴权、参数校验、落库和入队，Worker 负责执行。这样任务可以显示进度、失败原因，也方便后续做重试、取消和恢复。

### 可追问点

- 为什么没有直接用 Celery？
- 当前 Redis 队列有什么局限？

建议回答：

> 当前阶段为了快速掌控任务协议，使用 Redis RPUSH/BLPOP 自己实现轻量队列。后续如果需要定时任务、重试策略、并发控制和监控，可以迁移到 Celery 或更完整的任务系统，但业务层的 GenerationTask 协议可以保留。

## 8. 难点七：LLM 输出不稳定

### 问题

LLM 经常输出非标准 JSON、字段缺失、内容为空或混入解释文字。

### 当前解决方案

- `PromptBuilder` 要求输出固定 JSON 字段。
- `LLMClient` 统一调用 OpenAI-compatible API。
- 使用 JSON 提取和修复逻辑处理 fenced code、前后解释文字和部分格式错误。
- 没有 API Key 时走模拟生成，保证本地链路可测试。

### 面试表达

> 我把 LLM 调用封装成统一客户端，业务层不直接调用模型。这样以后切换模型供应商、增加重试、限流、JSON 修复和输出校验，都集中在一层处理。

### 后续增强

- 对每个 Agent 输出增加 Pydantic Schema 校验。
- 增加最大重试次数。
- 增加错误样本日志。
- 增加模型响应质量评分。

## 9. 难点八：如何把 LangGraph 用在真正有价值的地方

### 问题

如果只是“输入 Prompt -> 输出章节”，LangGraph 没有必要。真正需要图编排的是多阶段、有状态、可回写、可返工的流程。

### 当前落地

NovelForge 当前把 LangGraph 用在两个复杂流程：

| Graph | 价值 |
| --- | --- |
| `NovelProductionGraph` | 整本书生产循环，按剧情事件持续推进 |
| `EventGenerationGraph` | 一个事件内的规划、逐章生成、记忆同步、审校、修订、质量检查 |

### 面试表达

> 我没有为了用 LangGraph 而用 LangGraph。单章生成本身可以普通函数完成，但整本书生产和剧情事件生成是多节点、有状态、可能返工的流程，这才是图编排的价值点。

## 10. 项目架构总览

```text
Next.js Web
  -> FastAPI API
  -> PostgreSQL
  -> Redis
  -> Worker
  -> LangGraph
  -> LLMClient
  -> MinIO
```

关键设计：

- PostgreSQL 保存唯一事实。
- Redis 只做任务队列。
- MinIO 保存大文件。
- Worker 执行耗时任务。
- LangGraph 编排长流程。
- 前端只展示必要状态，减少用户心智负担。

## 11. 面试中可以重点讲的亮点

1. **从单章生成升级为剧情事件生成**：解决剧情碎片化。
2. **混合上下文策略**：最近 3 章全文 + 作品圣经 + 结构化记忆 + 风格向量。
3. **结构化记忆合并**：避免 Prompt 里堆重复事实。
4. **自动审校和修订闭环**：风险不是用户待办，而是系统处理记录。
5. **百万字样本异步分析**：MinIO + Worker + 切片 + Map-Reduce 聚合。
6. **统一异步任务协议**：所有长任务可追踪进度、失败和结果。
7. **LLM 解耦**：用户自填 API Key，后端通过 OpenAI-compatible 客户端统一调用。

## 12. 当前不足和后续计划

面试时可以主动说明当前项目仍有工程化增强空间：

| 不足 | 后续方案 |
| --- | --- |
| Agent 步骤日志还不完整 | 增加 `agent_step_logs`，保存每个节点输入输出 |
| 任务失败恢复较基础 | 增加重试、取消、断点恢复 |
| LLM 输出校验还可加强 | 增加 Pydantic Schema 和自动重试 |
| 样本分析仍是启发式指标 | 后续结合 LLM 做更高阶风格报告，但保留量化指标 |
| 缺少系统化测试 | 增加 API、Worker 和前端集成测试 |
| 云端部署尚未完全落地 | 后续补 Dockerfile、Nginx、CI/CD 和生产环境变量管理 |

## 13. 30 秒面试版本

> NovelForge 是一个长篇小说自动生成系统。我主要解决了直接用大模型写长篇时的三个问题：上下文不够、前后不一致、AI 味重。技术上，我用 FastAPI 做 API，PostgreSQL 存业务事实，Redis 做任务队列，Worker 执行异步 Agent，LangGraph 编排整本书和剧情事件生成。每章生成前会构建上下文包，包含最近 3 章全文、作品圣经、结构化记忆、审校风险和样本风格向量。章节生成后会自动抽取记忆、做连续性审校、自动修订。对于百万字样本，我用 MinIO 存原文，Worker 流式切片分析，再聚合成结构化风格报告，避免同步接口和上下文爆炸。

## 14. 2 分钟面试版本

> 这个项目的核心不是写一章，而是让系统能持续生产一本长篇小说。首先，我把用户输入收敛为起始需求文档，创建作品后自动生成作品圣经。然后自动生产不是按单章推进，而是按 6-12 章的剧情事件推进，使用 LangGraph 编排事件规划、章节生成、记忆同步、审校和修订。为了处理长篇上下文，我实现了 ChapterContextBuilder：最近 3 章全文保证语言连续性，结构化记忆保证事实连续性，作品圣经保证全局设定，样本分析风格向量保证文风约束。章节完成后，MemoryAgent 会抽取人物、关系、地点、事件等结构化记忆，并做实体合并，避免重复信息堆进 Prompt。质量方面，ContinuityChecker 和 EventQualityChecker 会自动发现风险，QualityAgent 会自动修订，前端只展示问题和修复历史，不把过程负担交给用户。样本分析这块我也做了异步架构：前端上传 TXT/MD，API 存到 MinIO，Worker 流式切片分析，最后聚合成可量化风格报告。整体上，这是一个围绕长文本、异步任务、Agent 图编排和结构化状态管理的工程项目。
