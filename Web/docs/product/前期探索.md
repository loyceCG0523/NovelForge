# NovelForge 前期探索

## 1. 项目定位

NovelForge 面向长篇网络小说自动创作，目标不是“让大模型写一章小说”，而是构建一套低用户干预的长篇小说生产系统。

理想使用方式：

```text
用户填写起始需求文档
  -> 系统生成作品圣经
  -> 系统按剧情事件规划 6-12 章
  -> 自动生成章节
  -> 自动同步结构化记忆
  -> 自动审校与修订
  -> 持续推进整本书
```

用户只在起始需求、账号设置、API Key 和少量高风险方向上做决策；普通剧情推进、章节生成、审校修订和记忆维护由系统自动完成。

## 2. 核心痛点

| 痛点 | 表现 | NovelForge 方案 |
| --- | --- | --- |
| 上下文长度不足 | 网络小说几十万到上百万字，无法全部放入模型上下文 | 最近 3 章全文 + 结构化长期记忆 + 作品圣经 + 样本风格向量 |
| 长篇一致性差 | 人物状态、伏笔、道具、地点和时间线容易前后矛盾 | 章节后自动抽取结构化记忆；生成前读取合并后的实体级记忆 |
| 剧情松散 | 一章一章生成容易变成流水账 | 以 6-12 章闭环剧情事件为生产单位 |
| AI 味明显 | 解释性对白、抽象情绪、模板句式、节奏平均 | 样本分析提取文风指纹；QualityAgent 审校与修订 |
| 用户不想管过程 | 用户不希望频繁决策、确认、修补 | 风险自动处理，前端只展示问题和修复历史 |

## 3. 当前产品原则

1. **低干预**：用户填写起始需求后，系统应尽量自动推进。
2. **事件驱动**：自动生成不以单章为核心，而以一个闭环剧情事件为核心。
3. **结构化优先**：人物、关系、地点、道具、事件、伏笔和规则必须结构化保存。
4. **上下文可回放**：每章生成时使用的上下文保存到章节快照中。
5. **风格工程化**：样本分析结果必须是可量化指标，不复制样本文本。
6. **风险自动处理**：连续性、剧情质量和风格问题由系统自动审校和修订。

## 4. 当前主流程

```text
注册 / 登录
  -> 创建作品
  -> 填写起始需求文档
  -> 自动生成作品圣经
  -> 上传优秀样本并生成风格报告（可选）
  -> 开始自动生成
  -> NovelProductionGraph 规划一个剧情事件
  -> EventGenerationGraph 生成 6-12 章
  -> 每章写入正文、摘要和上下文快照
  -> MemoryAgent 同步结构化记忆
  -> QualityAgent 审校并自动修订
  -> 工作台展示事件进度和风险历史
```

## 5. 起始需求文档

起始需求文档已经归入作品管理页，不单独作为主导航功能。

当前主要字段：

| 字段 | 作用 |
| --- | --- |
| 作品名 | 用户识别作品 |
| 题材 | 校园恋爱、奇幻悬疑、玄幻、都市等 |
| 目标字数 | 整本书目标 |
| 一句话需求 | 作品核心钩子 |
| 作品类型 | 长篇小说等 |
| 卖点与读者期待 | 爽点、情绪价值、阅读驱动力 |
| 主角设定 | 主角身份、目标、性格和起点 |
| 世界观 | 核心规则、组织、环境 |
| 剧情方向 | 中长期主线 |
| 每章字数范围 | 章节生成约束 |
| 风格参考 | 文风、节奏、对白要求 |
| 禁忌内容 | 不希望出现的套路或表达 |
| 自动化策略 | 系统推进和风险处理策略 |

## 6. 作品圣经

创建作品后，系统会先写入兜底作品圣经，再自动入队 `build_story_bible`。

作品圣经用于沉淀：

- 题材定位。
- 目标读者。
- 主角与关键角色。
- 世界观和核心规则。
- 主线冲突。
- 风格约束。
- 禁忌项。

当前产品策略是不把完整作品圣经作为复杂编辑器暴露给普通用户，只在作品管理中展示创作设定状态。

## 7. 剧情事件

当前自动生产不再只提供“启动章节 Agent”，而是以剧情事件为单位推进。

一个剧情事件通常覆盖 6-12 章，包含：

- 事件标题。
- 核心冲突。
- 章节范围。
- 章节计划。
- 事件级质量评分。
- 事件级风险。
- 自动修复次数。

这样可以避免一章一章生成导致的剧情碎片化。

## 8. 章节上下文策略

写第 `N` 章时，系统不会只读取第 `N-1` 章摘要。

当前上下文包包含：

| 类型 | 内容 |
| --- | --- |
| 近场上下文 | 最近 3 章全文和摘要 |
| 全局约束 | 起始需求文档、作品圣经 |
| 结构化记忆 | 合并后的人物、关系、地点、道具、事件、时间线、世界规则 |
| 伏笔与风险 | 未完成伏笔、开放或系统延后处理的审校风险 |
| 风格约束 | 样本分析风格向量、风格参考、禁忌内容 |
| 生产参数 | 目标章节、每章字数范围、自动化策略 |

上下文快照保存到 `chapters.context_snapshot`，用于排查生成质量。

## 9. 结构化记忆

当前结构化记忆已经实现：

- 章节完成后自动抽取。
- 同一实体记忆合并。
- 手动删除单个记忆组。
- 一键清空当前作品全部记忆。
- 删除章节时同步清理对应自动记忆。

记忆类型：

| 类型 | 保存内容 |
| --- | --- |
| 人物 | 身份、性格、状态、目标、关系、能力、家庭等 |
| 关系 | 人物之间的关系变化 |
| 地点 | 地点设定、状态、用途 |
| 道具 | 道具归属、用途、状态 |
| 事件 | 已发生事件和影响 |
| 时间线 | 时间顺序和关键节点 |
| 世界规则 | 世界观规则和约束 |
| 章节摘要 | 章节级压缩事实 |

Prompt 中不会简单塞入全部原始记忆，而是读取合并后的实体级记忆，降低重复和上下文浪费。

## 10. 样本分析

样本分析用于降低 AI 味并建立可复用风格。

当前架构：

```text
用户上传优秀小说 TXT/MD
  -> API 保存到 MinIO
  -> 创建 analyze_sample 任务
  -> Worker 流式读取
  -> 约 8000 字分片
  -> 分片抽取指标
  -> 聚合全书报告
  -> 写入 sample_analyses
  -> 后续章节生成读取风格向量
```

分析维度：

| 维度 | 指标 |
| --- | --- |
| 文风指纹 | 句子长度分布、比喻密度、感觉维度覆盖、叙事距离、对白占比、段落节奏 |
| 情绪曲线 | 情绪标签、情绪起伏、高潮位置、低谷位置 |
| 伏笔模式 | 埋设密度、兑现周期、埋设方式、误导策略 |
| 对白风格 | 角色话语长度、潜台词比例、打断频率、解释性对白比例 |
| 节奏模型 | 冲突间隔、信息释放速度、章尾钩子类型 |

样本分析只提取可迁移工程特征，不复制或保存样本原文到数据库。

## 11. 审校与自动修订

当前系统已实现：

- 章节连续性审校。
- 剧情事件级质量审校。
- 自动修订章节。
- 修订历史记录。
- 前端 ReviewIssuePanel 展示风险和修复历史。

产品原则：

```text
风险不是让用户处理的待办
风险是系统自动处理后的可解释记录
```

用户只需要知道系统发现了什么、修了几次、是否还有残留风险。

## 14. NovelForge 技术实现方案

当前代码已落地的技术栈：

| 层级 | 当前实现 |
| --- | --- |
| 前端 | Next.js App Router + React + 原生 CSS |
| API | FastAPI + Pydantic v2 + SQLAlchemy 2 + Alembic |
| Worker | Python Worker + Redis BLPOP/RPUSH |
| Agent 编排 | LangGraph，用于整本书生产图和剧情事件生成图 |
| 数据库 | PostgreSQL + pgvector 镜像 |
| 对象存储 | MinIO，S3 兼容接口 |
| LLM | OpenAI-compatible Chat Completions，用户在设置页填个人 API Key |
| 本地部署 | Docker Compose 启动 PostgreSQL、Redis、MinIO |

当前系统架构：

```text
Next.js Web
  -> FastAPI API
  -> PostgreSQL
  -> Redis
  -> Worker
  -> LangGraph / LLM
  -> MinIO
```

## 15. 后续方向

下一阶段优先级：

1. 增加 Agent 步骤日志，保存每个节点输入输出快照。
2. 增加任务取消、失败重试和断点恢复。
3. 将样本风格报告进一步转化为可调生成策略。
4. 加强真实 LLM 输出的 JSON 稳定性和质量评估。
5. 增加书稿导出。
6. 增加自动化测试和 CI。
