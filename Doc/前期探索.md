# NovelForge 前期探索

## 1. 项目定位

NovelForge 面向长篇网络小说自动创作，目标不是提供一个单纯的写作 Agent，而是构建一套“长篇小说生产系统”。

用户理想使用方式：

```text
填写起始需求文档 -> 系统自动规划 -> 自动生成章节 -> 自动审校返工 -> 持续输出书稿
```

系统应尽量减少用户在创作过程中的参与。用户主要提供初始方向，后续的剧情规划、人物设计、伏笔安排、章节生成和质量检查由系统自动完成。

## 2. 核心问题

当前大模型直接写长篇小说，主要存在三类问题：

| 问题 | 表现 | 设计要求 |
| --- | --- | --- |
| 上下文不足 | 网络小说常达到几十万到上百万字，无法整体放入模型上下文 | 使用近场全文上下文和结构化长期记忆 |
| 长篇一致性差 | 容易遗漏人物状态、伏笔、道具位置、剧情因果 | 所有记忆必须结构化保存，并在每章后更新 |
| AI 味明显 | 常出现模板句式、过度解释、抽象情绪描写 | 建立文风指纹和反 AI 句式规则 |

因此，NovelForge 的核心能力不是“生成一段文字”，而是持续管理长篇小说的状态、结构和风格。

## 3. 总体架构

系统可分为五层：

| 层级 | 作用 | 关键模块 |
| --- | --- | --- |
| 用户层 | 管理账户、额度、数据导出、创作偏好和自动化策略 | User Center、Personalization、Data Export |
| 输入层 | 接收用户初始需求，并自动补全创作规格 | NovelBrief、Brief Expander |
| 规划层 | 设计全书方向、世界观、人物、主线和章节队列 | Creative Director、Plot Planner |
| 记忆层 | 管理设定、人物、伏笔、时间线和章节状态 | StoryBible、CharacterState、ForeshadowRegistry |
| 生产层 | 组装上下文、生成章节、审校、改写、返工 | Context Builder、Writer、Review Agents |

其中 `Creative Director` 是系统的决策中枢，负责在用户低干预的前提下统一创作方向，并替用户做大部分常规创作决策。

## 4. 输入与低干预模式

用户只需要填写一份起始需求文档 `NovelBrief`。字段应支持不完整输入，系统通过 `Brief Expander` 自动补全缺失信息。

```yaml
作品类型: 玄幻
目标字数: 80万字
目标读者: 男频
平台风格: 起点
核心卖点: 废柴逆袭、家族秘密、宗门成长
主角设定: 边境小城少年，身世隐藏巨大秘密
禁用内容: 可选
参考作品风格: 可选
章节字数: 每章3000字
```

用户也可以只输入一句话：

```text
写一本男频玄幻长篇，主角从边境小城崛起，有家族秘密，风格爽快但不要太白。
```

系统只在重大方向变化时询问用户，例如改变主角核心人设、更换作品类型、让重要角色死亡、引入争议内容或大幅偏离原始需求。普通章节中的角色出场、伏笔位置、对白写法和小冲突解决方式应由系统自动决策。

## 5. 上下文策略

写第 `N` 章时，不能只依赖第 `N-1` 章摘要。推荐上下文由两部分组成：

| 类型 | 内容 | 作用 |
| --- | --- | --- |
| 近场全文上下文 | 第 `N-1`、`N-2`、`N-3` 章全文 | 保证文风、节奏、情绪和对白连续 |
| 远场结构化上下文 | 人物状态、伏笔记录、地点状态、道具状态、剧情时间线 | 保证设定、因果和长线一致性 |

此外，系统应按需检索与当前章节相关的历史片段，例如某人物过往出场、某伏笔埋设片段、某地点描写或某道具状态变化。

## 6. 结构化记忆

长期记忆必须结构化保存，章节摘要只能作为辅助信息。建议核心数据结构如下：

| 结构 | 保存内容 |
| --- | --- |
| StoryBible | 世界观、规则体系、组织势力、地点、历史事件、禁止冲突项 |
| CharacterState | 身份、目标、已知信息、隐瞒信息、人际关系、能力状态、位置、持有物、语言风格 |
| PlotTimeline | 已发生事件、事件时间、涉及人物、因果关系、后续影响 |
| ForeshadowRegistry | 伏笔名称、埋设章节、埋设方式、当前状态、预计兑现章节、实际兑现章节 |
| ChapterState | 本章目标、冲突、新增事实、状态变化、未解决问题、章尾钩子 |
| StyleFingerprint | 句长分布、段落长度、对白占比、动作描写密度、心理描写方式、禁用句式 |

每章生成完成后，`State Extractor` 必须从正文中抽取状态变化，并更新以上结构。

## 7. 样本分析能力

为了降低 AI 味并建立可复用风格，系统需要支持对用户上传的优秀小说样本进行分析，生成结构化参考报告。

重点分析维度：

| 维度 | 指标 |
| --- | --- |
| 文风指纹 | 句子长度分布、比喻密度、感觉维度覆盖、叙事距离、对白占比、段落节奏 |
| 情绪曲线 | 每章情绪标签、情绪起伏、高潮位置、低谷位置 |
| 伏笔模式 | 埋设密度、兑现周期、埋设方式、误导策略 |
| 对白风格 | 角色话语长度、潜台词比例、打断频率、解释性对白比例 |
| 节奏模型 | 冲突间隔、信息释放速度、章尾钩子类型 |

样本分析结果不直接复制具体内容，只提取可迁移的工程特征。

## 8. 反 AI 风格控制

AI 味需要单独处理，不能只依赖“写得自然一点”这类提示词。系统应维护 `AIPatternBlacklist`，用于识别和改写高频模板表达。

```json
{
  "禁用句式": [
    "不是...而是...",
  ],
  "限制倾向": [
    "连续使用抽象情绪词",
    "用总结句替代具体动作",
    "过度使用仿佛、似乎、猛然、微微、一瞬间",
    "人物对白过于完整、正确、解释性过强"
  ],
  "改写原则": [
    "用动作替代情绪说明",
    "用具体物件承载心理变化",
    "减少抽象形容词",
    "对白保留停顿、误解、打断和潜台词",
    "章尾悬念优先来自具体事件"
  ]
}
```

该模块应在风格改写之后执行，作为最终文本清理的一部分。

## 9. Agent 分工

| Agent | 职责 |
| --- | --- |
| Creative Director | 统一创作方向，替用户做默认决策 |
| Brief Expander | 将简短需求扩展为完整创作规格 |
| Plot Planner | 生成主线剧情、分卷大纲和章节目标 |
| Context Builder | 组装前三章全文、结构化记忆和检索片段 |
| Writer Agent | 根据章节规划和上下文生成正文 |
| State Extractor | 从正文中抽取结构化状态变化 |
| Continuity Checker | 检查人物、道具、地点、伏笔和时间线一致性 |
| Foreshadow Manager | 管理伏笔埋设、推进和兑现 |
| Style Agent | 应用文风指纹并改写文本 |
| AI Pattern Cleaner | 清理 AI 高频句式和模板化表达 |
| Final Reviewer | 综合审校，并决定是否返工 |

## 10. 章节生产流程

推荐流程：

```text
NovelBrief
  -> ExpandedBrief
  -> StoryBible
  -> VolumeOutline
  -> ChapterPlanQueue
  -> Context Builder
  -> Chapter Draft
  -> State Extraction
  -> Continuity Check
  -> Style Rewrite
  -> AI Pattern Clean
  -> Final Review
  -> Memory Update
  -> Manuscript Output
```

自动返工规则：

| 问题 | 处理 |
| --- | --- |
| 连续性错误 | 必须返工 |
| 人物行为严重偏移 | 必须返工 |
| 本章无有效剧情推进 | 重写章节细纲 |
| 伏笔遗漏 | 修改章节计划或补写段落 |
| AI 句式过多 | 进入句式清理 |
| 风格偏移明显 | 进入风格改写 |

## 11. 当前结论

NovelForge 的优先建设方向应是：

1. 低干预输入和需求自动扩展。
2. 用户账户、额度、数据导出和个性化策略。
3. 近场全文上下文加结构化长期记忆。
4. 人物、伏笔、时间线、道具和地点的状态管理。
5. 章节级自动生成、审校和返工流水线。
6. 文风指纹和反 AI 句式控制。

只有先解决状态管理和审校机制，长篇小说自动生成才可能稳定推进。

# NovelForge 技术实现方案

## 1. 最终技术选型

NovelForge 不做多套技术备选，直接采用以下技术栈：

| 层级 | 固定选型 | 原因 |
| --- | --- | --- |
| 前端 | Next.js App Router + TypeScript + Tailwind CSS + shadcn/ui | 适合 SaaS 控制台、表单、编辑器和服务端渲染页面 |
| 后端 API | Python FastAPI + Pydantic v2 + SQLAlchemy 2 + Alembic | Python 更适合 Agent 和大模型生态，FastAPI 适合快速构建清晰 API |
| Agent 编排 | LangGraph | 章节生产是长流程、多步骤、可恢复任务，LangGraph 的持久化和状态图模型最适配 |
| 异步任务 | Celery + Redis | 章节生成、样本分析、审校返工都是长任务，不能阻塞 API 请求 |
| 主数据库 | PostgreSQL 16 + pgvector | 结构化数据和向量检索统一放在 PostgreSQL，降低系统复杂度 |
| 对象存储 | 阿里云 OSS | 保存导出稿件、样本文件、任务快照和大体积日志 |
| 云服务 | 阿里云 ECS + RDS PostgreSQL + Tair Redis + OSS | 面向国内部署最稳，后续备案、域名、HTTPS 和运维路径清晰 |
| 部署方式 | Docker Compose + Nginx + Certbot | MVP 阶段足够稳定，成本低，部署链路简单 |
| 模型接入 | LLM Gateway 自建适配层 | 业务代码不直接绑定某一家模型，便于切换 OpenAI、通义千问、DeepSeek 等模型 |

结论：第一版不要上 Kubernetes，不要拆微服务，不要引入独立向量数据库，不要把前后端部署到多个平台。MVP 要优先保证链路简单、可观测、可恢复。

## 2. 最终系统架构

```text
浏览器
  -> Next.js Web
  -> FastAPI Backend
  -> PostgreSQL + pgvector
  -> Redis
  -> Celery Worker
  -> LangGraph Agent Runtime
  -> LLM Gateway
  -> 大模型服务
  -> OSS
```

核心原则：

1. 所有用户请求先进入 FastAPI。
2. 所有生成类任务只创建任务，不同步等待结果。
3. Celery Worker 执行 LangGraph 章节生产图。
4. PostgreSQL 保存业务事实和结构化记忆。
5. pgvector 只做语义召回，不保存唯一事实。
6. OSS 保存大文件和可回放快照。
7. 前端通过任务接口轮询，后续再升级 WebSocket。

## 3. 推荐代码仓库结构

采用单仓库多应用结构：

```text
NovelForge/
  apps/
    web/                 # Next.js 前端
    api/                 # FastAPI API 服务
    worker/              # Celery + LangGraph Worker
  packages/
    shared-schema/       # 前后端共享类型、OpenAPI 生成代码
  infra/
    docker/
    nginx/
    scripts/
  docs/
  docker-compose.yml
  .env.example
```

`apps/api` 和 `apps/worker` 都使用 Python，但职责要分开：

| 应用 | 作用 |
| --- | --- |
| api | 用户登录、作品管理、章节读取、任务创建、状态查询 |
| worker | 执行章节生成、样本分析、审校返工、记忆抽取 |

## 4. 数据库落地设计

第一版必须先建这些表：

| 表 | 必须字段 |
| --- | --- |
| users | id、email、password_hash、plan、created_at |
| user_preferences | user_id、default_genre、chapter_words、automation_level、style_rules |
| projects | id、user_id、title、genre、target_words、status、current_chapter_id |
| novel_briefs | id、project_id、raw_input、expanded_json、status |
| chapters | id、project_id、volume_no、chapter_no、title、content、word_count、status、version |
| chapter_plans | id、chapter_id、plan_json、status |
| generation_tasks | id、project_id、chapter_id、type、status、progress、current_step、error_message |
| agent_step_logs | id、task_id、step_name、input_snapshot、output_snapshot、created_at |
| story_bibles | id、project_id、data_json |
| character_states | id、project_id、name、state_json、updated_chapter_id |
| foreshadows | id、project_id、name、status、plant_chapter_id、expected_resolve_chapter_id、data_json |
| timeline_events | id、project_id、chapter_id、event_json |
| review_issues | id、project_id、chapter_id、task_id、type、severity、status、detail_json |
| text_chunks | id、project_id、chapter_id、chunk_type、content、embedding |

关键约束：

1. `chapters.content` 保存正文最终稿。
2. `agent_step_logs` 保存每一步输入输出，便于排错和回放。
3. `text_chunks.embedding` 使用 pgvector。
4. 所有结构化记忆字段先用 `jsonb`，等字段稳定后再拆成强结构列。

## 5. Agent 编排图

LangGraph 中固定实现一个章节生产图 `ChapterProductionGraph`：

```text
load_project_state
  -> build_context
  -> write_chapter_draft
  -> extract_state_changes
  -> check_continuity
  -> check_foreshadow
  -> rewrite_style
  -> clean_ai_patterns
  -> final_review
  -> persist_memory
  -> publish_chapter
```

每个节点的输入输出都必须是 JSON，不允许节点之间传自由文本。

节点职责：

| 节点 | 输出 |
| --- | --- |
| build_context | context_pack_json |
| write_chapter_draft | draft_text |
| extract_state_changes | state_patch_json |
| check_continuity | continuity_report_json |
| check_foreshadow | foreshadow_report_json |
| rewrite_style | styled_text |
| clean_ai_patterns | cleaned_text、pattern_report_json |
| final_review | pass / rewrite_required |
| persist_memory | memory_update_result |
| publish_chapter | chapter_version |

返工规则写死在图里：

| 条件 | 流向 |
| --- | --- |
| 连续性高风险 | 回到 `write_chapter_draft` |
| 伏笔遗漏 | 回到 `build_context` 或 `write_chapter_draft` |
| AI 句式超阈值 | 回到 `clean_ai_patterns` |
| 风格偏移 | 回到 `rewrite_style` |
| 审校通过 | 进入 `persist_memory` |

本地先启动 PostgreSQL、Redis、MinIO：

### 第 6 步：实现第一条闭环

第一条闭环必须是：

```text
注册
  -> 登录
  -> 创建作品
  -> 填写起始需求
  -> 生成 ExpandedBrief
  -> 创建第 1 章 ChapterPlan
  -> 创建生成任务
  -> Worker 生成章节草稿
  -> 前端看到任务完成
```

不要先做复杂编辑器，也不要先做完整样本分析。第一阶段必须先打通任务链路。

## 7. 云端部署方案

云端固定采用阿里云：

| 资源 | 规格 |
| --- | --- |
| ECS | Ubuntu 24.04 LTS，2 核 4G 起步 |
| RDS | PostgreSQL 16，开启 pgvector |
| Redis | Tair / Redis 兼容版，1G 起步 |
| OSS | 一个 bucket，保存样本、导出文件、任务快照 |
| 域名 | novel-forge.example.com |
| HTTPS | Nginx + Certbot |
| 镜像仓库 | 阿里云容器镜像服务 ACR |

MVP 阶段所有业务容器放在一台 ECS 上：

```text
ECS
  - nginx
  - web
  - api
  - worker
  - celery-beat

RDS PostgreSQL
Tair Redis
OSS
```

PostgreSQL 和 Redis 不放在 ECS 本机，直接使用云服务，减少运维风险。

## 8. 云端从 0 部署步骤

### 第 1 步：购买云资源

1. 购买阿里云 ECS：Ubuntu 24.04 LTS，2 核 4G，40G 系统盘。
2. 购买 RDS PostgreSQL 16。
3. 购买 Tair Redis 兼容版。
4. 创建 OSS Bucket。
5. 创建 ACR 镜像仓库。
6. 如果要正式使用域名，先完成域名备案；未备案前可先用 IP 测试。

### 第 2 步：初始化 ECS

```bash
ssh root@your_server_ip
apt update && apt upgrade -y

curl -fsSL https://get.docker.com | bash
apt install -y docker-compose-plugin
ufw allow 22
ufw allow 80
ufw allow 443
ufw enable
```

### 第 3 步：配置云数据库

在 RDS 中创建：

```sql
CREATE DATABASE novelforge;

GRANT ALL PRIVILEGES ON DATABASE novelforge TO novelforge_app;
```

然后在安全组中只允许 ECS 访问 RDS 和 Redis。

### 第 4 步：准备生产环境变量

### 第 6 步：生产 docker-compose

服务器 `/opt/novelforge/docker-compose.yml`：


## 9. CI/CD 流程

使用 GitHub Actions 或 Gitee Go 均可，但项目流程固定为：

```text
push main
  -> run tests
  -> build web/api/worker images
  -> push ACR
  -> ssh ECS
  -> docker compose pull
  -> docker compose up -d
  -> alembic upgrade head
```

第一版可以手动部署，但从第二版开始必须接入 CI/CD，否则 Agent 类项目迭代会非常痛苦。

## 11. 必须坚持的工程规则

1. 大模型输出必须经过 Pydantic Schema 校验。
2. 每个 Agent 节点必须保存输入快照和输出快照。
3. 章节生成必须异步执行。
4. 结构化记忆必须由数据库保存，不能只放向量库。
5. 向量检索结果必须可追溯到章节和片段。
6. 返工必须有明确原因，不能只写“质量不佳”。
7. 用户默认低干预，只有高风险方向变化才提醒。
8. 云端数据库、Redis、OSS 密钥不得写入代码仓库。
